시작할 때 `AGENTS.md`(릴리스 작업 규칙 원문)와 `docs/work/` 의 해당 작업 파일을 읽는다.

## 1. 무엇이 바뀌었나

```
git log $(git describe --tags --abbrev=0)..HEAD --oneline
```

## 2. 버전 판정

| 올림 | 언제 |
|---|---|
| patch | 오류 수정, 작은 개선 |
| minor | 새 기능 |
| major | 기존 사용 방식의 큰 변경 |

**배포할 변경 묶음당 한 번만** 올린다.

## 3. 두 곳을 함께 고친다

- `config.py` 의 `APP_VERSION`
- `release_notes.py` 의 `RELEASE_NOTES` — 같은 버전 항목을 **맨 뒤에** 추가. 기존 항목은 보존.

`release.sh` 가 이 누락을 막지만, 막히고 나서 고치지 말고 처음부터 함께 쓴다.

## 4. 상담사용 안내 문안

읽는 사람은 **상담사 4명**이다.

- 쉬운 한국어. 코드 용어(Blueprint·셀렉터·마이그레이션)를 쓰지 않는다.
- **바뀐 점 / 사용 방법 / 주의점** 순으로.
- ⚠ 아직 구현하지 않은 것을 완료한 것처럼 쓰지 않는다.
- ⚠ 의료법 위반 표현(효과 단정·완치 보장)을 쓰지 않는다.

## 5. 내보내기

```
./release.sh --check     # 검사만 — 먼저 이걸 돌린다
./release.sh             # 통과하면 태그 생성 + push
```

## 6. 운영 배포

```
ssh bokju-nas "sudo -n /root/deploy.sh --yes"
```
NAS가 [백업 → 최신 태그 교체 → 재빌드 → 재시작 → 확인]까지 한다.
되돌리기는 `--yes` 대신 `--rollback` (**사용자가 요청할 때만**).

- `bokju-nas` 를 못 찾거나 비밀번호를 물으면 SSH 연결이 안 잡힌 것이다.
  메시지를 그대로 보여주고 **임의로 우회하지 않는다.**
- 상담 업무시간(09~18시)이면 재시작 순간 저장이 유실될 수 있음을 **한 번 알린다**(그래도 진행).

## 절대 규칙

- ⚠ **"푸시 완료"와 "서버 적용·공지 게시 완료"를 구분해서 보고한다.** 섞어 말하지 않는다.
- NAS 안의 파일을 직접 고치지 않는다 — 다음 배포에 덮어써지고 기록도 안 남는다.
- 기능 코드를 고치지 않는다. 배포 중 문제가 보이면 배포를 멈추고 보고한다.

## 끝낼 때

작업 파일의 `## ⑤ 내보냄` 절**만** 채운다 — 버전·판정 근거, 안내 문안, 태그, 배포 결과.
