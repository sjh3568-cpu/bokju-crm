## ① 무엇을  — `plan`

**배경**

사용자가 문자 기능의 빈틈 6가지를 지적했다(2026-09-28): 수신자 이름 검색 없음, 발송 전 확인 없음(회수 불가),
템플릿 분류가 병명군뿐, 상담 후 안내를 잊음, 수신 결과를 모름, 여러 명 발송 불가.

확인된 사실:
- **발송사 계약 전**(사용자 답 2026-09-28). 지금은 `manual` 모드로 동작하고, 상담사는 **개인 휴대폰**으로 보호자에게 문자를 보낸다.
- manual 모드의 '전송'은 `sms:` 링크라 PC 브라우저에서는 대부분 아무것도 안 열리는데, 이력에는 '수동'으로 남는다.
  개발 DB(운영 사본)의 `sms_log`는 0건이다.
- 운영 서버는 사내망 전용이라 발송사가 결과를 우리에게 보내 줄 수 없다(웹훅 불가). 수신 결과는 우리가 주기적으로 조회해야 한다.
- 시점별 기준 날짜가 채워진 비율(개발 DB, 최근 60일):
  상담 275건 중 보호자 번호 268건(97%) · 입원예정일 16건(6%) · 재원 389명 중 퇴원예정일 0건 ·
  퇴원 157명 중 보호자 번호 146명(93%) · 원무 명부는 매일 적재됨.

**하려는 것 (묶음 A·B·C)**

### A. 수신자 이름 검색 + 발송 전 확인

1. **수신자 검색** — '최근 상담 200건' 드롭다운을 검색칸으로 바꾼다.
   환자 이름이나 번호 뒷자리로 찾고, 검색은 기존 `/api/autocomplete/patient`를 그대로 쓴다.
   환자를 고르면 새 API `GET /api/sms/recipient?pid=`가 최근 상담의 보호자 이름·번호와 토큰 값(입원예정일·주치의),
   질환군을 돌려준다. 이 API가 `window.SMS_CONSULTS` 인라인 목록을 대체한다.
   `/sms?cid=`로 들어오면 지금처럼 그 상담이 미리 선택된다.
2. **확인 창** — '전송' 버튼을 '확인하고 보내기'로 바꾼다. 확인 창에는 받는 사람(이름·번호), 휴대폰 미리보기,
   단문/장문 구분이 나온다.
   - **미치환 토큰(`SMS_PLACEHOLDERS`)이 남았거나 번호 형식이 틀리면 보내기 버튼을 끈다.**
   - 서버 `/api/sms/send`도 같은 조건으로 400을 돌려준다(화면을 거치지 않는 호출까지 막는 이중 방어).
3. **휴대폰으로 넘기기(manual 모드)** — 확인 창에 `SMSTO:<번호>:<본문>` QR을 띄운다.
   - 상담사가 개인 휴대폰 카메라로 찍으면 문자앱이 번호와 본문이 채워진 채 열린다.
   - QR은 서버가 SVG로 만든다(`segno`, 순수 파이썬). 외부 CDN은 쓰지 않는다. 엔드포인트는 `POST /api/sms/qr`.
   - 상담사가 **'보냈어요'**를 눌러야 `sms_log.status='phone'`으로 기록한다. QR을 띄우기만 한 것은 기록하지 않는다.
   - 기존 `manual` 이력은 그대로 두고, 화면 라벨만 '수동(확인 안 됨)'으로 바꾼다.
4. **발송사를 연동한 뒤(live·test)** — 같은 확인 창의 버튼이 곧바로 발송한다. 흐름은 바뀌지 않는다.

### B. 템플릿 분류 2축 — 대상 질환 × 시점

- `sms_templates.template_group`은 그대로 두고 **'대상 질환'**으로 이름만 바꿔 부른다
  (공통·중추신경계·근골격계·비사용증후군·기저질환).
- 새 칸 `sms_templates.timing`을 추가한다. 목록 `config.SMS_TIMINGS`는
  **상담 직후 / 입원 전날 / 입원 당일 / 퇴원 당일 / 퇴원 후 / 수시**이고, 기본값은 '수시'다.
- 기존 템플릿 이전(`_ensure_columns` 뒤 1회, 멱등):
  - 시드 이름 '입원 예정 안내' → 입원 전날
  - 나머지 시드 3개 → 상담 직후
  - 그 밖(운영에서 직접 만든 것) → 수시. 잘못 분류될 일을 막으려고 추측하지 않는다.
- **문자 화면** — 템플릿 목록을 시점 탭으로 나눈다. 수신자의 최근 상담 질환군과 '공통' 템플릿만 보여 주고,
  '전체 보기'로 필터를 푼다. 질환군 판정은 목록 필터와 같은 기준(`DISEASES_GROUPS`, `consultations.diseases`)으로
  하는 새 함수 `models.consult_disease_groups(consult)` 하나로 한다.
- **템플릿 관리 화면** — 대상 질환·시점 두 칸을 모두 고르게 한다.

### C. 깜빡 방지 알림 — 대시보드 '오늘 처리 필요'의 '안내 문자'

- `models.sms_reminders(today)` 하나가 오늘 보내야 할 안내를 만든다.
  `_dashboard_action_queue`에 구분 **'안내 문자'**로 넣는다(기존 구분별 탭에서 따로 볼 수 있다).

  | 시점 | 대상 | 근거 |
  |---|---|---|
  | 상담 직후 | 상담일로부터 `SMS_CONSULT_FOLLOWUP_DAYS`(7일) 안, 보호자 번호가 있는 상담 | `consultations` |
  | 입원 전날 | 입원예정일 = 내일, 아직 입원 전 | `consultations.planned_admission_date` |
  | 입원 당일 | 오늘 입원(외진 복귀 제외) | `models.admission_flow_events(오늘, 오늘)` IN |
  | 퇴원 당일 | 오늘 퇴원(외진 나감 제외) | 같은 함수 OUT |
  | 퇴원 후 | 퇴원일 = 오늘 − `SMS_AFTER_DISCHARGE_DAYS`(3일) | 같은 함수 OUT |

  입·퇴원은 **`admission_flow_events` 하나만** 쓴다(CLAUDE.md 단일 근거 규칙). 따로 세지 않는다.
- **알림 켜고 끄기 = 템플릿** — 그 시점에 **사용 중인 템플릿이 하나 이상 있어야** 알림이 나온다. 별도 설정 화면은 없다.
- **알림 하나를 가리키는 키(`reminder_key`)**
  - 상담 직후: `상담 직후:c<상담id>`
  - 그 밖: `<시점>:p<환자id>:<기준일>`
- **보냄 처리** — 알림 행의 '문자'를 누르면 `/sms?reminder=<key>`가 열리고, 수신자와 그 시점의 템플릿이 채워진다.
  확인 창을 거쳐 `sms_log`(새 칸 `reminder_key`)에 status `sent/test/phone`로 기록되면 알림이 사라진다.
- **안 보냄 처리** — 사유 한 줄(예: 전화로 안내함)을 받아 새 테이블 `sms_reminder_closures(reminder_key UNIQUE,
  patient_id, consultation_id, reason, closed_by, created_at)`에 기록하면 알림이 사라진다.
  감사 로그 action은 `sms_reminder_close`이고, `AUDIT_ACTION_LABELS`에 라벨을 추가한다.
- **상담 상세** — '보호자 안내 문자' 한 줄을 추가한다. 이 상담의 알림 상태(보낼 것 / 보냄 n건·마지막 날짜 / 안 보냄 사유)와
  '문자' 버튼을 보여 준다. 이 한 줄이 대시보드와 같은 `sms_reminders` 결과를 쓴다(같은 숫자는 한 함수).
- 자동 발송은 하지 않는다. 사람이 확인 창을 거쳐 보낸다.

**안 할 것**

- 여러 명 동시 발송(⑥)과 수신 결과 추적(⑤) — 발송사 계약 후에 따로 설계한다.
  결과 추적은 사내망 제약 때문에 발송사 결과 조회 API를 폴링하는 방식이 된다.
- 예약·자동 발송 — 발송사 계약 후, C의 알림 큐를 발송사로 연결하는 방식으로 붙인다.
- 입원예정일·퇴원예정일 입력을 늘리는 일(그래서 '입원 전날'은 예정일을 적은 건만 알린다).
- 시점별 템플릿 문구 작성 — 상담실이 템플릿 관리에서 쓴다. 요청하면 초안을 따로 준다.
- 상담사 휴대폰 번호 관리, 카카오 알림톡.
